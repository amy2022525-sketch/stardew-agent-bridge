# 两层游玩日志

目的：中断后快速恢复，不重复消费动作；用少量可检索经验减少无效尝试。玩家要求的游玩日志是宿主工作记录，不是修改 Codex/其他软件全局记忆的授权。

## 1. 先确定保存位置与作用域

有文件工具时，在宿主已授权的可写工作目录下保存：

```text
playlogs/<world-key>/<agent-key>/
  short-term.md      当前检查点，覆盖更新
  long-term.md       当前长期目标与经验索引，合并更新
  days/              按需追加每个游戏日/会话的压缩摘要
```

`world-key` 用宿主生成的安全 ASCII 标识映射真实 `(profileId, worldId, actorFarmerId)`，不能直接把外部显示名、存档名拼进路径；在日志头记录这个映射。`agent-key` 区分 owner，避免两位 Agent 同写一个检查点。共享计划须先协调写入者。

不要写入安装目录、Skill 本身、只读发行包或版本控制的攻略文件。本项目忽略 `playlogs/`，但在其他目录仍需确认不上传私有记录。默认不收录钥匙、账号、完整本机路径、截图原始大文本或玩家私密信息。

仅 MCP 时使用 [记忆工具方式](bridge-playbook.md#3-使用-bridge-记忆保存日志)。两种存储若同时存在，明确哪份是主本及最后同步时间，不互相无限复制。存储不可用时向玩家输出短期与长期两个可复制摘要，标注未持久化；先停止危险的在途动作，再报告问题。

## 2. 短期：随时可续玩

按 [短期模板](../assets/short-term.template.md) 填写实际值；没有观察就写未知，不补猜。

必须含：

- schema/version 与 owner；现实记录时间；真实世界、角色、profile 及可用代次；游戏年/季/日/时间与采样时点。
- 当前玩家要求、1 个小目标、成功条件，以及预算、资源预留、体力/生命/时间停止条件。
- 最近观察的位置、工具槽位、水量、背包余量、生命/体力、金币；只记录当前目标需要的字段。
- 已核验进展与证据来源，仍未做的部分；快照未覆盖的地块保持未知。
- 每个未决 actionId、工具/意图、prepared / in_flight / unknown 状态、查询途径；自动任务另记 taskId 和最近 stateVersion。
- 下一步可执行的小动作、执行前必须重验的条件、控制/接管状态及保存状态。

重要资源动作前先写 prepared，成功返回或核验后再更新；prepared 不是“未执行证明”。同类低风险动作每做完一个可核验的小区就合并一次；建议不超过约 5–10 个已确认动作才存检查点，状态变化或异常不等批次。

恢复时：

1. 比对当前世界、角色与 profile；不同则切换日志，不能执行旧待办。
2. 读 `stardew_status` 和当前快照；检查玩家接管及存档/日期变化。
3. 逐项核对未决 ID 或后台 taskId。原请求可能已生效；不重放。日期变更后旧浇水完成记录只是历史。
4. 用真实状态重写当前检查点，再继续下一小步。过期 session、targetRef、contextToken 不恢复使用。

## 3. 长期：规划与经验

按 [长期模板](../assets/long-term.template.md) 维护四类内容：

| 类别 | 内容与证据 | 何时修订 |
| --- | --- | --- |
| 目标 | 玩家希望、优先级、阶段、依赖和完成条件 | 玩家改方向、约束变化或里程碑 |
| 稳定进展 | 已解锁设施、已证实的配方/路线、任务里程碑，附游戏日期及来源 | 观察新证据或地图改变 |
| 资源预留 | 种子/食物/工具/建造预算，目标物品和数量，不当作当前余额 | 准备交易、目标切换 |
| 经验与假设 | 触发条件 → 操作 → 实际结果 → 下次怎么做；验证次数、反例、有效范围 | 新试验或重复失败 |

资源余额、当前 NPC 位置、库存、作物是否已浇水是短期事实，不能当永久长期事实。经验示例的正确形式是“在某版本/地图/季节/条件下观察到 X，下一次先核实 Y”，不是“永远这样做”。单次样本可记“暂定经验”，不包装成稳定结论。

长期目标用 `planned / in_progress / verified_done / blocked / dropped` 区分；准备动作、接单或模型说完成都不能标 verified_done。审核型成果明确 `main_reviewed`。路线由玩家决定，不把自己的优化偏好改写成玩家偏好。

游戏日结束、会话结束或里程碑发生时，压缩为几条：完成了什么、资源关键差分、哪条计划变化、哪次失败教训、明日先做什么。跨日复盘只在日子真的推进后发生，不能为了完成复盘而自行睡觉。

## 4. 控制上下文成本

- 开始只读 short-term、long-term 的目标概览和当前任务相关 3–5 条经验；需要追因才查对应 days 摘要。
- 短期保留当前检查点与最近几条关键差分，建议 ≤1000 中文字；长期主文件建议 ≤2000 中文字，旧日流水移入 days，失效结论保留失效原因。
- 同类失败合并为一条经验，保留频次和一次代表性证据；不要把每个 move / select 都写进长期日志。
- 去重和压缩不能抹掉未决动作、未知保存状态、作用域或证据等级。不要把自然语言日志当作权威动作账本。
- 有 CAS 的记忆使用真实 revision 更新；文件修改先重读，使用宿主支持的安全替换方式，避免上下文压缩后覆盖别人新写的内容。

## 5. 效率复盘

每轮挑一个相关指标：完成的可核验目标数、成功动作/总尝试、重复失败、走回头路、模型调用数/已知 token、日志读取量。只记录确实能测到的数据；API usage 未知则记 unknown，不估算成 0。

把“瓶颈 → 小改动 → 下次如何比较”写成一条待验假设，例如先处理同一区域再出门。比较时说明存档、天气、任务与装备是否相同，不用不同条件下的耗时声称效率提升。日志规则已实现不等于自主游玩效率已实测提升。
